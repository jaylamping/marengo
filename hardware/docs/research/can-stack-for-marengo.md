# Build marengo's CAN layer on plain SocketCAN

**Use this:** one isolated, classic-CAN USB adapter per bus running **mainline candleLight firmware** (the Openlight Labs CANable Pro class, STM32F0-based, about $60). Linux sees each one as a native SocketCAN `canN` through the in-kernel `gs_usb` driver. On top of that, run **one Rust realtime process** built on the `socketcan` 4.0 crate. It has one blocking, SCHED_FIFO thread per bus doing "send every command, collect every reply before a deadline". Below that sits a small hand-written RobStride codec that does no I/O and stays in the drive's default private protocol. The drive's own CAN timeout (parameter `0x7028`) is set to 50 ms. Every frame goes to MCAP with a kernel timestamp, and `candump -L` runs alongside as an independent black box. The same binary runs against a simulated drive on `vcan`. Across all six industries the research covered, nobody's best practice is a heavier protocol stack. Small CAN robots run a vendor protocol over several parallel 1 Mbit/s buses, with one deterministic exchange per tick and drive-side watchdogs. What marengo should borrow from automotive, drones and aerospace is their health-monitoring vocabulary, not their protocols. Two things need fixing before any money is spent. First, the compute plan's "CANable 2.0 Pro isolated class" adapters use an STM32G431, and **mainline candleLight does not support that chip**. Second, the power-board plan's STM32G474 + candleLight bridges have the same problem. Both are explained below. I checked the RobStride protocol facts the notes left open against the four vendor CAN 2.0 manuals, and they hold up, with two documentation errors to watch.

## The stack, and where to start

| Layer | Pick | Why this one |
|---|---|---|
| Interface | 1 × isolated gs_usb/candleLight adapter per bus (CANable Pro class, STM32F042/F072), bought one at a time as limbs come online | Mainline driver and firmware, buffers on the device (which fixes the MCP2515 overruns), hardware RX timestamps, isolation |
| Linux | 64-bit Pi OS, `ip link set canN up type can bitrate 1000000 sample-point 0.75` (explicit timing), `berr-reporting on`, no `restart-ms` in motion, default `txqueuelen` 10 | Errors show up instead of turning into hidden queueing |
| RT setup | `isolcpus` on 2 cores, SCHED_FIFO, `mlockall`, CPU governor `performance`. Move to a 6.12+ PREEMPT_RT kernel only if the measured cycle misses its budget | Measure first (tenet 6) |
| Rust | `socketcan` 4.0 (blocking `CanSocket`, features `netlink` + `dump`), `rtrb` for realtime ↔ non-realtime handoff, `thread-priority` for SCHED_FIFO, `mcap` for logs, `metrics` + Prometheus exporter | Current, widely used, no async runtime |
| Protocol | Your own sans-IO `robstride` codec: a typed frame table transcribed from the manuals, per-model scales as data, test vectors taken from the manual, cross-checked against `motorcom` | No existing crate meets the bar |
| Loop | Control thread + 5 bus threads. Each tick: write all type-1 commands, poll for type-2 replies until about 60% of the period, publish a snapshot with per-joint age | Copies what the pi3hat does in hardware |
| Safety | Drive `canTimeout` = 1000 (50 ms), read back before every enable; stop on any fault bit, on N missed replies, or on bus-off; never auto-clear | Tenet 3, checked against the manuals |
| Logging | MCAP (raw + decoded + injected-fault channels) from the runtime, plus a `candump -L` systemd service per bus | Off-the-shelf viewers: Foxglove, Rerun, PlotJuggler |
| Sim | `vcan0`–`vcan4` + one Rust sim-drive process with built-in fault injection, driven by the same codec | Same binary; faults with no risk to a motor |

The start-here order for the left arm (can1, IDs 11–15):

1. Buy **one** isolated candleLight adapter. Confirm that `dmesg` shows `gs_usb` (not `slcan`/ttyACM) and that `ip -details link show can1` reports it.
2. Write the codec and its manual-vector tests.
3. Write the sim drive and bring the loop up on `vcan1`.
4. Wire the real arm and check the stock bus with `candump`/`canbusload`.
5. Measure round-trip latency and per-cycle jitter on the Pi 5 at 250 Hz.
6. Only then buy the other four adapters and decide on PREEMPT_RT.

## Six industries, one pattern: vendor protocol, parallel buses, drive watchdogs

Legged and humanoid robots split into two camps by price. Low-cost actuators (RobStride, CubeMars, Mini-Cheetah-style) run 1 Mbit/s CAN with MIT-style command/reply ([humanoid.guide](https://humanoid.guide/?p=19658)). Higher-end research humanoids choose EtherCAT for 1–4 kHz loops: the full-size Berkeley Humanoid chose it for latency, not cost ([Liao et al. 2024](https://arxiv.org/pdf/2407.21781)). Unitree's motors use 4 Mbit/s RS-485 at 6 kHz ([RoboSavvy](https://robosavvy.co.uk/unitree-8010-motor.html)). The closest peer to marengo is the **Berkeley Humanoid Lite**. It uses **four gs_usb USB-CAN adapters, one bus per limb, CAN 2.0 at 1 Mbit/s, and runs the actuator loop at 250 Hz** on a mini PC ([BHL paper](https://arxiv.org/pdf/2504.17249v1); [BHL docs](https://berkeley-humanoid-lite.gitbook.io/docs/in-depth-contents/can-communication)). That is direct evidence that marengo's target works on cheap USB adapters. Every faster system pushes timing into one tight exchange per tick, often on dedicated hardware: the mjbots pi3hat (5 CAN-FD buses over SPI), Ben Katz's SPIne SPI-to-quad-CAN bridge, and the ODRI Ethernet master board with a 0.2 ms round trip ([mjbots](https://blog-575.pages.dev/2024/05/16/optimizing-moteus-command-rate); [SPIne](https://github.com/bgkatz/SPIne); [ODRI](https://raw.githubusercontent.com/open-dynamic-robot-initiative/master-board/HEAD/README.md)). mjbots measured about 800 Hz per moteus over USB against about 2200 Hz over SPI, and advises derating "by 2x or more" for application time. At 250 Hz marengo is far inside both numbers.

The other industries each contribute one idea, not a stack. **Industrial** CANopen contributes a per-node state machine (Pre-operational → Operational → Stopped) and a strict split between cyclic PDO traffic and acyclic SDO parameter traffic ([CiA NMT](https://www.can-cia.org/can-knowledge/canopen/network-management)). **Automotive** contributes conservative bus budgeting: about **70% load is the practical ceiling**, and buffers should absorb a 10 ms burst at 100% load ([Copperhill](https://copperhilltech.com/blog/tag/Busload)). It also contributes AUTOSAR E2E's receiver-side classification of every message as OK, lost, repeated or wrong-sequence ([AUTOSAR PRS E2E](https://www.autosar.org/fileadmin/standards/R22-11/FO/AUTOSAR_PRS_E2EProtocol.pdf)). **Drones** (DroneCAN/Cyphal) contribute a one-frame heartbeat with uptime (an uptime that goes backwards means the node rebooted) and a four-level health enum ([DroneCAN §6](https://dronecan.github.io/Specification/6._Application_level_functions); [Cyphal Health](https://rust-digger.code-maven.com/src/cyphal-dsdl-0.0.9/assets/Health.1.0.dsdl)). **E-bike/EV** VESC firmware contributes the rule that a motor stops when commands stop arriving: the default timeout is 0.5 s, and VESC calls setting it to 0 "strongly discouraged" ([VESC comm_can](https://gitea.interbiznw.com/rusefi/bldc/raw/commit/4499982f993bdc777134b8cf07c5c3fdd040864b/documentation/comm_can.md)). **Aerospace** CANaerospace contributes priority bands in the ID space and a mandatory "who's there" identification service ([CANaerospace](https://wikiwand.com/en/articles/CANaerospace)). For marengo, those ideas become a host-side node table (state, last seen, fault bits, reply latency), a startup scan that refuses to enable unless every skeleton ID answers, and per-drive miss counters. No humanoid was found running full CiA 402 or Cyphal on its joint bus. EtherCAT, a CANopen stack, AUTOSAR layering, J1939 and dynamic node IDs are all overkill here, and RobStride's fixed protocol rules most of them out anyway.

The bus budget fits. An extended-ID, 8-byte frame takes about 131–155 µs at 1 Mbit/s, so one command plus one reply costs about 0.31 ms per drive. This is arithmetic, not a measurement. The left arm's 5 drives at 300 Hz load the bus to about 47%. A 6-drive leg loads it to about 56% at 300 Hz and about 37% at 200 Hz. Both are under the 70% ceiling, but only with exactly one exchange per drive per tick, so parameter reads must fit into leftover slack. **Run 250 Hz as the default**, and treat 300 Hz as something to earn by measurement.

## The adapter decision, and two plan risks to fix now

The current HAT fails because the MCP2515 holds only two received frames. A 4–5 ms host stall at 1 Mbit/s can deliver roughly 25–35 frames, so frames are lost. A USB adapter that buffers on its own microcontroller absorbs the stall, and its frames arrive late instead of not at all. Among USB adapters, gs_usb/candleLight is the right family. It has been a mainline driver since 2013, it handles high bus load well, and **gs_usb reads the adapter's 1 µs hardware timestamps since Linux 6.1** ([Pengutronix](https://pengutronix.de/en/blog/2023-01-30-yes-we-can-add-new-features.html); [canable.io](https://canable.io/getting-started.html)). The Openlight CANable Pro is fully galvanically isolated, classic CAN up to 1 Mbit/s, with a termination jumper and a CANH/CANL/GND terminal, for $60 ([Openlight Labs](https://reach.dog/shop/openlight-labs/products/canable-pro-isolated-usb-to-can-adapter)). It runs mainline candleLight, but it ships with slcan, so flash it or buy it pre-flashed. One quirk to know: candleLight echoes a sent frame when it reaches the CAN peripheral, not when it is actually on the wire, so TX timestamps are approximate ([candleLight_fw](https://github.com/candle-usb/candleLight_fw)).

**Risk 1, compute plan.** The compute plan specifies "CANable 2.0 Pro isolated class" adapters. Those boards use an STM32G431, and the candleLight README says G431 devices such as the CANable-MKS 2.0 are **"not supported by this project yet"** ([candleLight_fw](https://github.com/candle-usb/candleLight_fw)). The pull request adding G4, multichannel and FD support (#176) was still unmerged in October 2025. Commenters there report USB resets on some MKS hardware ([PR #176](https://github.com/candle-usb/candleLight_fw/pull/176)). Marketplace "CANable 2.0 Pro" clones are often sold as "USB to PCAN" analyzers ([example listing](https://www.fruugo.ca/canable-20-pro-usb-can-analyzer-module-170-mhz-operating-frequency-efficient-performance-processor-usb-to-pcan-converter-module/p-414388017)). They usually ship slcan or a community fork, and slcan is a serial-line protocol that is worse for latency and has no hardware timestamps. Change the plan to name an F0-based mainline-candleLight board, and test one before buying five.

**Risk 2, power board.** The PDB plan and design README assume two STM32G474s running "candleLight/gs_usb firmware". Mainline candleLight has no G4 support, and the project's own rationale log already notes that a `budgetcan_fw` fork and board configuration would be needed. Rev B dropped the on-board bridges, so this is dormant. If the bridges ever come back, though, they mean owning a firmware fork. Don't revive them without budgeting for that.

**Is the upgrade worth it?** The steelman is PEAK PCAN-USB FD: isolated to 500 V, 1 µs timestamps, high-speed USB (125 µs microframes instead of 1 ms frames), mainline `peak_usb`, and CAN FD. It costs about **£280 per channel** ([Control Tech UK](https://controltech.uk.com/products/pcan-usb-fd)), roughly five times as much. Full-speed USB adds up to about 1 ms of receive jitter. That is the largest jitter source, but at a 4 ms period it is acceptable. BHL's 250 Hz on gs_usb is the evidence. Buy PEAK only if the Pi 5 measurement in step 5 shows jitter eating the budget. An MCP2518FD HAT has deep buffers and a well-maintained driver but only two channels. A pi3hat is built for moteus at 5 Mbit/s FD, and its Pi 5 compatibility is unverified.

**CAN FD.** The CAN 2.0 manuals all specify **CAN 2.0, 1 Mbit/s, 29-bit extended frames, 8-byte data**. RobStride also publishes CAN FD manuals ([RobStride/Product_Information](https://github.com/RobStride/Product_Information), `Product Literature/CANFD/`, RS00 to RS10P, dated 2026-05-29). Checked after the draft: those describe separate CAN FD versions of each model ("the articulated motor uses the CANFD communication mode", with its own USB-CANFD tool). marengo's drives run today on the classic-only MCP2515 HAT, so they are the CAN 2.0 versions, and classic adapters lose nothing. FD only matters if a future purchase is a CAN FD model; then that bus would need an FD adapter, and every drive on it would have to be FD.

## The RobStride protocol, checked against the vendor manuals

I extracted the RS00, RS02, RS03 and RS04 CAN 2.0 manuals in `hardware/docs/robstride/` with `pdftotext` and checked each open fact. **The 29-bit ID layout is confirmed.** Bits 28–24 are the communication type, bits 23–8 are "data area 2", and bits 7–0 are the destination address (§4, all four manuals). In the type-1 operation-control (MIT) frame, the **feed-forward torque travels in ID bits 23–8**. Data bytes 0–7 carry position, velocity, Kp and Kd as big-endian u16. The type-2 reply carries the motor ID in bits 15–8, **fault flags in bits 21–16** (undervoltage, overcurrent, overtemperature, encoder, stall/overload, uncalibrated), and **mode in bits 23–22** (0 reset, 1 calibration, 2 run), with the host ID in the low byte. Its data bytes hold angle, velocity, torque and temperature×10. The codec should take its scales from the skeleton's actuator type, using the values I read from the type-1 tables:

| Model | Torque | Velocity | Kp | Kd |
|---|---|---|---|---|
| RS00 | ±14 Nm | ±33 rad/s | 0–500 | 0–5 |
| RS02 | ±17 Nm | ±44 rad/s | 0–500 | 0–5 |
| RS03 | ±60 Nm | ±20 rad/s | 0–5000 | 0–100 |
| RS04 | ±120 Nm | ±15 rad/s | 0–5000 | 0–100 |

Angle is ±4π on every model. The **host-loss timeout is confirmed as `0x7028 canTimeout`** (uint32, default 0 = disabled, **20000 = 1 s**), so tenet 3's 50 ms is the value **1000**. When it fires, "the motor enters the reset mode" (§3.3.6): it disables, it does not hold position. For a humanoid that means limp, so the host must stop first. **Protocol switching is type 25**: data byte value 0 = private protocol (default), 1 = CANopen, 2 = MIT. It "requires reboot", and the separate MIT protocol has its own command 8 for switching back (§4.1.12, §4.2.4, §6.11). **Active reporting is type 24**, off by default, with a 10 ms default interval tunable via `EPScan_time` `0x7026` (§4.1.11, §4.2.1). The damper switch is `0x702A`, default 0.

Two documentation errors matter. The type-2 fault table lists bit 20 twice ("uncalibrated" and "gridlock overload"). The type-24 reply table looks copy-pasted from the command, since it shows target angle and Kp. So decode fault bits defensively, check them on a real drive, and **leave active reporting off**. Command/reply gives one frame per drive per tick and per-tick liveness for free. The third-party crates confirm the layout but not their own quality. The kscalelabs `robstride` crate (last release May 2025) encodes torque over ±100 but decodes it over ±120, panics on malformed frames, matches replies only by motor ID, and assumes RS04 feedback for every model ([robstride actuator.rs](https://docs.rs/crate/robstride/0.3.6/source/src/actuator.rs); [supervisor.rs](https://docs.rs/crate/robstride/0.3.6/source/src/supervisor.rs)). `motorcom` 1.1.1 has a clean sans-IO encoder with tests such as "torque_goes_into_extra_data_not_data_bytes", which makes it the right cross-check ([motorcom](https://crates.io/crates/motorcom)). Seeed's and `kcan`'s base-ID schemes (0x200+id) belong to the MIT protocol mode, not the default private protocol ([Seeed wiki](https://wiki.seeedstudio.com/robstride_control/)). Write the codec yourself: one `FrameSpec` row per manual table, each citing its section, with tests built from the manual's own worked example (§3.3.5 decodes `90 07 e8 0c` as type 18, host 0xFD, motor 1).

## Loop, safety, logging and sim, sized to tenets 3, 5 and 8

**Realtime loop.** One process owns all five sockets. Each bus thread opens a blocking `socketcan::CanSocket` with a kernel filter for its own reply IDs, error frames enabled through `CAN_RAW_ERR_FILTER`, and kernel timestamps through `read_frame_with_timestamp` (added in socketcan 3.6) ([socketcan CHANGELOG](https://raw.githubusercontent.com/socketcan-rs/socketcan-rs/master/CHANGELOG.md)). On each tick the control thread publishes a command array per bus. The bus thread writes the type-1 frames in fixed skeleton order, then polls with the time remaining until about 60% of the period. It matches replies in a fixed array indexed by motor ID, then publishes positions with per-joint age and miss count. Parameter reads and writes (types 17 and 18) go only into the slack after that deadline, at most one or two per tick. Nothing in the loop allocates. Frames go to the logger as plain records over an `rtrb` ring ([rtrb](https://crates.io/crates/rtrb)). Use no tokio: the K-Scale supervisor shows the cost of async here. It holds a write lock across awaits and drops state updates without notice when its 32-slot channel fills. The Berkeley `actuator-control` crate's "receive thread plus cached state" model is the nearest good template ([actuator-control](https://raw.githubusercontent.com/berkeley-humanoids/actuator-control/HEAD/README.md)). Treat ENOBUFS as "tick overcommitted": count it and drop the frame. Don't raise `txqueuelen`. The kernel developers kept the default at 10 precisely so that overload surfaces as an error instead of as latency ([LKML](https://lore.kernel.org/lkml/87sgvvnwqf.fsf@taht.net/T/)). Reported Pi 5 PREEMPT_RT worst cases are about 10 µs idle and 50–110 µs under heavy load ([linux-rt-users](https://spinics.net/lists/linux-rt-users/msg28144.html)). That is why RT is a cheap fallback if the stock kernel's jitter fails the measurement.

**Safety**, one rule per failure. The drive layer: write `canTimeout`=1000, the torque, current and speed limits, and the damper on. Read all of them back with type 17 before every enable, and refuse to enable on any mismatch. The host layer: any non-zero fault bit or a mode other than "run" stops the limb, and stays latched until the operator clears it. Three consecutive missed replies stop the limb, well before the drive's 50 ms timeout makes it go limp. Bus-off on any bus stops the robot. Leave `restart-ms` off outside bench mode, because a bus that silently restarts mid-gait is unsafe. Per-drive health is a synthetic heartbeat built from each reply (alive, fault bits, mode, temperature), shown in one node table.

**Logging and metrics.** The runtime writes MCAP: one raw channel per bus (`{bus, id, dlc, data, t_kernel, t_mono, dir}`), decoded joint channels, and an injected-fault channel. Foxglove, Rerun and PlotJuggler all open the result ([MCAP](https://mcap.dev/guides/getting-started); [Rerun](https://github.com/rerun-io/rerun)). No standard CAN-in-MCAP schema exists, so the schema is yours. Separately, a `candump -L` systemd service per bus records a crash-proof black box that `canplayer`, python-can and cantools read without conversion ([can-utils](https://github.com/linux-can/can-utils)). DBC is a poor fit because RobStride puts payload inside the ID, so skip it. Export kernel CAN health (state, berr counters, bus-off, restarts, overruns from `ip -details -statistics link` ([kernel docs](https://docs.kernel.org/networking/can.html))) together with reply-latency histograms and miss counts. Use the `metrics` crate on a non-realtime thread and scrape it with Prometheus/Grafana. Mirror the same numbers into MCAP for the replay loop, because a 15 s scrape is too coarse for 250 Hz.

**Sim.** Create `vcan0`–`vcan4` ([kernel docs](https://docs.kernel.org/networking/can.html)) and run one Rust sim-drive process. It answers type 1/3/4/17/18 from the same codec, simulates `canTimeout`, and injects faults from a seed: silence, late replies, fault bits, wrong mode. Building fault injection into the sim, instead of running a separate proxy, saves a process. Real bus behaviour that vcan cannot fake, such as error counters and bus-off, can be exercised with `canerrsim`. vcan has no bit timing, so sim tests check logic, not bus load.

## Conclusion

The research reframes the rewrite. marengo's CAN problem was never protocol sophistication. It was a two-frame receive buffer, plus a plan that quietly assumed firmware support that doesn't exist for the G4 chips it named. Fix the buffer with a $60 mainline-candleLight adapter, and what's left is small enough to read in one sitting: a codec transcribed from four vendor tables, a send-all/collect-all loop, and one 50 ms number written into every drive and read back before every enable.

What remains uncertain is quantitative and cheap to settle on the bench: the Pi 5's USB round-trip jitter with five gs_usb adapters, whether the stock kernel is good enough, how quickly RobStride replies, and confirming the model label on each drive says CAN 2.0. Each is a single logged test on the left arm, and each could move a number in the table above, but none should change the shape of the stack.
