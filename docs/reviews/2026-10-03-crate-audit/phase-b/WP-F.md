# WP-F — Dual command source and single motion owner

Branch `audit/wp-f`. Verified against main at `cc47280f` (post c879b6a, RS03 ±20, POST_SET_ZERO_QUIET 800 ms, firmware-timing analyzer). Design and operator rules: [docs/safety.md "Single motion owner"](../../../safety.md#single-motion-owner-stdin-vs-chappe).

## Design in one paragraph

A **motion lease** inside `marengo-pi` (`bins/marengo-pi/src/motion_owner.rs`). Exactly one source — stdin or Chappe — owns motion for the life of the process. The owner is **claimed at launch** (`--motion-owner stdin|chappe`, or `MARENGO_MOTION_OWNER`; default `chappe`, which is what the systemd service and Consul need) and **released when the process exits**; there is deliberately no runtime hand-over. MCP claims stdin for every scripted session by exporting `MARENGO_MOTION_OWNER=stdin` in the one shared remote preamble (`tools/marengo-pi-mcp/src/env.ts`). Commands are classified: **Stop** (stdin `disable`/`quit`/`hold-off`/`impedance-off`, Chappe `enable(false)`) is always accepted from either source and never needs ownership; **Observe** (status, status-poll, Active Reporting lease) is accepted; **Motion** (enable, home/Set Zero, hold/wave/torque/mode, Testing batches, runtime kp/kd tuning) is accepted only from the owner. A refusal is logged, printed (stdin) and published as `ActionEvent{action:"motion_refused", accepted:false, reject_reason}` on `robot/audit/action`. No proto change was needed (existing `ActionEvent`), so no regen or `buf lint` run.

## NEEDS-DECISION

**D1 — Consul Testing UX after an operator Disable (and fresh-process auto-enable).** Consul's Testing page posts Position batches with no Enable, relying on the implicit re-arm. Conservative default implemented: after an *operator* disable (stdin `disable`, Chappe `enable(false)`, lag stop) motion commands refuse until an explicit enable, so "Disable then Start" on the Testing page now does nothing until Enable is pressed on the Hardware page; the refusal is only in the log and the `robot/audit/action` stream because Consul does not consume that topic yet. A process that was never operator-disabled keeps the implicit enable (needed by Consul Testing from a fresh start and by existing MCP flows).
  - Options: (a) keep as implemented; (b) also make Testing surface `motion_refused`/`ExplicitEnableRequired` in Consul (toast from `robot/audit/action`) — recommended next; (c) require explicit enable from a fresh process too (strictest; breaks Testing-from-fresh and needs Consul + MCP script review).
  - Recommendation: (a) now, (b) as a small Consul follow-up.

**D2 — `wave:<joint>:…` encoded inside `MitJointCommand.name`.** The magic mode number is fixed; the in-band command string is a wire hack (CS19, contracts P17). Proper fix is proto-first: add a `WaveCommand` message / `repeated WaveCommand waves` to `MitCommandBatch`, regenerate (`cd consul && npm run gen:proto`, keep `buf lint` green), update `compound-runner.ts`, the gateway validator (which now parses the string) and `parse_testing_wave_command`. Needs a coordinated Consul + Pi deploy. Recommendation: do it, but as its own PR; not safety-critical now that the gateway canonicalises and validates the string.

**D3 — `ControlLoop::set_control_mode` silent no-op while a reference is busy (and Davout's duplicate guard).** Not reachable from `marengo-pi` after this WP (see verdict). Making it return `Result<(), LoopError>` touches ~45 call sites (mostly tests) and the motor-repl bin. Recommendation: defer; do it with the WP-D Berthier API pass.

**D4 — ownership transfer.** Ownership is process-lifetime on purpose. Options: runtime hand-over (stdin `release-motion`, Chappe claim message → proto change) vs. static. Recommendation: static; restart with the other flag.

## Bench-behaviour impact (read before the next session)

* `marengo-pi` started by hand (SSH, `profile-pi-loop.sh` is updated) now defaults to **Chappe-owned**: typed `enable`/`hold-at`/… are refused with `… refused: motion is owned by chappe` unless launched with `--motion-owner stdin` (or `MARENGO_MOTION_OWNER=stdin`). MCP tools get stdin automatically (deploy the MCP together with the new binary; a new binary with an old MCP refuses all scripted motion).
* While an MCP session runs, a Consul tab can still **Disable** (stops the arm; the script's later `hold-at` then fails with `drives were disabled by an operator`), but its Enable, Set Zero, Testing batches and runtime kp/kd retunes are refused. Set Limits / config overlay (configuration plane) are not gated.
* `robot/enable` floods that overflow the 256-slot channel now stop the drives instead of being half-applied.
* Testing gain overrides sent while the loop is in GravityComp/TorqueOnly/Disabled are rejected with a warn, rather than silently dropped; a Position batch from GravityComp now actually carries its kp/kd.
* Gateway: `/command/testing_mit` rejects joints outside the command allowlist (403), caps flood at 20/s, and `/command/enable` with `enable=true` is capped at 2/s (Disable never).
* Status-poll and Active Reporting lease (diagnostic Chappe commands) remain accepted from a non-owner during an MCP session; they send type-4/type-24 frames but cannot move a drive. Not changed.
* Stdin EOF still does not stop `marengo-pi` (L-marengo-pi-17, WP-O); with stdin ownership and a script that omits `quit`, nobody can command motion until SIGTERM, but Stop from Consul still works.
* Not run: bench/hardware verification (no Pi access needed for the software evidence above). Suggested bench check after deploy: `pi_hold_on`, then press Start on the Consul Testing page — expect the hold to stay put and a `motion_refused` event in `robot/audit/action`; press Disable in Consul — expect the hold to stop.
