## 0. Legend and method

**Matrix columns.** Each row gives: id | invariant | source | enforcing code (`path:line` and symbol) | test(s) that would fail if the invariant were violated | bench evidence | status.

**How code rows are referenced.** Documented-rule rows often point at a code row id such as `DV-47`. Those code rows are defined in Appendices A–D, which carry the full code and test citations.

**Test verification.** A test is listed only if the enumerating agent opened it and saw an assertion on the variant, fault class, wire trace or value.
- "(name)" means the test was mapped by its name and comments only.
- "exercises only" means the test runs the path without asserting the invariant.

**Status values.** Exactly one of five:

| status | meaning |
|---|---|
| `enforced+tested` | Code enforces the rule and a test asserts it. |
| `enforced-untested` | Code enforces it, but no test asserts it. |
| `documented-unenforced` | A document states the rule and no code enforces it. Procedural operator rules land here. |
| `enforced-undocumented` | Code enforces a rule that no document states (code-only rows). |
| `contradicted` | The document says X and the code does Y. |

**Compound rules use the weakest link.** When a documented rule has several clauses, its status is the weakest clause, and the notes name that clause. For example, one untested clause makes the whole row `enforced-untested`.

**Enumeration.** Five passes:
1. Documented rules were extracted by hand from the sources in §1. Each bullet or numbered item that states a requirement is one row. The counting rules are in §1.
2. Code invariants were enumerated by four parallel read-only passes. Their patterns and hit counts are reproduced at the top of each appendix. The patterns used:
   - every `enum *Error|*Reason|*Kind|FaultClass` variant;
   - every `fault_authority.record(` and `record_receive(` site, and every `latch_control_fault(` site;
   - every `Err(DavoutError::…)`, `LoopError::`, `HoldError::`, `BusError::`, `CommandError::` and `ReferenceError::` site;
   - every `fail_reference(` call and every revocation call (`.revoke()`, `revoke_binding`, `revoke_joint`, `revoke_selected`);
   - every `return Err(` / `Err("…")` in `bins/marengo-pi` and `bins/motor-repl`;
   - fail-open scans (`let _ =`, `.ok()`, `unwrap_or`).
3. **Fault/latch census.**
   - `FaultClass` has 10 variants (`crates/davout/src/faults.rs:9-20`).
   - `fault_authority.record*` has 15 production sites: 5 in `lib.rs` (1163, 1218, 1298, 1957, 2411), 8 in `feedback_consumer.rs` (343, 393, 424, 445, 597, 661, 673, 686) and 2 in `reference_transaction.rs` (981, 1580).
   - Berthier latches only through `latch_control_fault` (3 sites, `crates/berthier/src/loop.rs:1034-1045`). Robstride and the bins latch nothing themselves.
   - Every one of these sites is a row in Appendix A, B or C.

## 6. Ten worst gaps, ranked by consequence

The ranking key is the worst credible physical outcome: uncontrolled motion in the operator workspace first, then loss of a stop path, then silent degradation of a safety check. "Hard to reach" lowers a gap's rank only when it is shown.

1. **No runtime defense against a wrong gravity model or sign in GravityComp.** This is the upright-pose incident class (safety.md:59-61).
   - The wrong-sign watchdog is disabled on master (control.yaml:216-217; ADR0015:6-15), and its latch is untested (DV-22).
   - The per-joint sign test is only an operator token (reference_queue.rs:111-113), not the pulse procedure in safety.md:67.
   - The only τ_g-plausibility gate is in MCP tooling (tools/marengo-pi-mcp/src/gravity-gate.ts). Consul/Chappe enable bypasses it, and also skips marengo-pi's gravity-saturation preflight (bins/marengo-pi/src/main.rs:339-358 vs :881-887). That preflight fails open on a torque error: `unwrap_or(0.0)` at main.rs:834 and motor-repl main.rs:49.
   - HoldTracking catches a wrong model only in Position mode, after 2 s.
   - The elevated-arm guard in AGENTS.md:195 does not exist (BT-15).
   - Bench evidence: on 2026-10-03, a τ_g error of −1.6 Nm pushed the pitch off target (handoff-2026-10-03-right-arm-urdf.md:13).
2. **The only master danger zone is inert in the modes used, and the documented fault action does not exist.**
   - `elevated_shoulder_pitch_fall` is `clamp_velocity` (control.yaml:203-211), which edits only the MIT velocity field (lib.rs:2780-2786).
   - The MIT torque term for velocity is kd·(v_des−v). GravityComp runs kd=0 (control.yaml:50-53) and Position runs `kd_mit = 0` (rust-patterns.md:222), so the clamp has no physical effect in either mode.
   - "Clamp or fault" is contradicted (C2), and with no pose the rule evaluates the commanded position (C3).
3. **Software stop paths are not dependable.**
   - (a) `motor-repl disable` builds the full Supervisor before stopping (MR-01; safety.md:233-236). It is the stop that `pi_motor_disable` and `pi_hold_off` use, with errors swallowed: `motor-repl disable … || true` (tools/marengo-pi-mcp/src/tools/motion.ts:206, :559).
   - (b) motor-repl has no SIGTERM/exit disable (C4).
   - (c) A Chappe disable whose `disable_all` errs returns before setting the control mode Disabled (main.rs:360-363).
   - (d) Lagged Chappe channels silently drop pending enable/disable messages (`let Ok(bytes) = rx.try_recv() else { break; }`, main.rs:482).
   - (e) The hardware E-stop input is not wired to software (S-50), so software Disabled never reflects the E-stop line.
4. **No watchdog independent of the control thread, and the drive-side CAN timeout is never configured.**
   - The comm watchdog runs inside the same 200 Hz tick (lib.rs:1980-2052). A hung, blocked or killed loop leaves the drives holding the last MIT frame, including τ_g feed-forward.
   - Loop overrun is only counted (main.rs:1450-1457, :1529-1551; PI-51).
   - `ParameterId::CanTimeout` exists (crates/robstride/src/params.rs:34), but no production code writes or reads it back (grep: only definitions and a test). Prior review recorded the same (docs/reviews/2026-09-29/control.md:286).
5. **Total torque is unbounded; only τ_ff is capped** (prior CS10, ledger status `open`).
   - Davout rejects kp/kd only above the per-motor_type maxima (lib.rs:2599-2604) and caps τ_ff (lib.rs:2663-2667). kp·(q_des−q) is bounded only by the Berthier lead clamp (BT-43).
   - Robstride saturates finite out-of-range MIT values rather than rejecting them (mit.rs:70-91; RS-07, untested).
6. **Reference acquisition error exits can leave the target drive enabled.**
   - After `ArmTarget` writes Enable, the error-propagating `?` exits in `advance_reference` return with the reservation armed and no `finish_reference` stop: receive `acquire` at reference_transaction.rs:1099-1101, "installed target disappeared" at :1052-1054 and :1107-1109, `phase_deadline` at :1300, `motor_position_scale` at :1336.
   - `calibrate_joint_zero` then returns `HomingVerify` without `disable_all` (lib.rs:924-931); only the deadline branch disables (:940-946).
   - Not tested. Contradicts ADR0026:62-66 (C10).
7. **The bench-incident fuse is untested where it latches.**
   - No ControlLoop test drives `tick()` into `HoldTracking`, so the latch, stop and intent discard at loop.rs:1042-1057 are unverified (BT-35).
   - The wave exemption is untested (BT-40), and none of the three fault reason strings is asserted.
   - AscentStall watches positive-direction moves only (position_hold.rs:1066-1068), so negative outbound stalls rely on HoldTracking.
8. **"zero_sta/add_offset/type-22 never sent" holds only because nothing calls them.**
   - The public `encode_write_parameter`/`write_parameter_at` accept `ZeroSta`/`AddOffset` (params.rs:38-40, :81-83, :126-174), and raw `send_frame` is public (bus.rs:261).
   - The guarding test checks only `from_u8(22)`.
   - A future caller could silently persist a firmware zero shift across power cycles, which the reference design assumes never happens (ADR0036:157-159).
9. **Position trace I/O inside the 200 Hz tick.**
   - `flush()` is never called, which meets AGENTS.md:197 to the letter. But the 512 KiB `BufWriter` performs a synchronous `write(2)` from `tick_inner` when full (position_trace.rs:32, :47-58; loop.rs:1303-1342).
   - The error is discarded (loop.rs:1337), and an open failure is swallowed (`.ok()`, position_trace.rs:20).
   - This is the same watchdog class the rule exists for. It is env-gated (`MARENGO_POSITION_TRACE`).
10. **The Davout MIT-path limit envelope is untested, and its documents disagree.**
    - No test asserts a clamped value through `filter_mit_core` (lib.rs:2605-2643; DV-44). The post-clamp hard check is unreachable (DV L-4).
    - The margin's velocity source contradicts ADR0009:34 (C5), and the measured-slack code defaults (0.005) contradict the ADR's 0.03 (C6).
    - The Set Limits "measured q outside new bounds" check reads a sample map that is empty outside Active, so in practice it never fires (limit_envelope.rs:65-79; lib.rs:2399; DV L-3).

**Prior-review linkage.** Gap 4 is the same as control.md:286. Gap 5 is CS10 (open). Gap 3(e) is noted in safety.md:152 and position-hold-control-review.md. Gaps 1, 2, 6, 7, 8, 9 and 10 have no open ledger entry.

### Contradictions / leads

Answers to parent's extra checks first (E1–E8), then leads (L-n). Leads, not verdicts.

- **E1 Wrong-sign (ADR 0015:6-15).** `config/control.yaml:216-221` `enabled: false` (only control.yaml in tree). Code path is live but short-circuits at `crates/davout/src/lib.rs:2692` → status **dormant** (DV-22). All unit tests force `enabled = true` (lib.rs:4742) and call `filter_mit_command`, which never latches; nothing asserts `FaultClass::WrongSign` or a stop. ADR 0015 Context (lines 25-30) describes opposition to *measured velocity*; code compares sign(τ_ff) with a sign table on sign(q) (lib.rs:2709-2716) and only uses |dq| as a gate; also joint-space τ vs motor-space schema (the ADR's own stated reason for disabling).
- **E2 ADR 0009:25-26.** Command: clamp then `Limit` if outside hard (lib.rs:2621-2643) — but in the batch path `Limit` is a non-latching rejection (filter at lib.rs:2160-2168), not a "fault"; and it is unreachable because `effective_command_bounds` clips to [soft, soft] ⊂ hard (armee-kinematics/src/limits.rs:105-111). Measured: `feedback_consumer.rs:853` → `Limit` → `FaultClass::Feedback` latch + disable (lib.rs:1181, 1901-1903); only while Active (feedback_consumer.rs:198-205, 835-837). Slack: serde default 0.03 (marengo-config/src/lib.rs:563-566) and every joint sets 0.03, but `LimitMarginConfig::default()` = 0.005 (armee-kinematics/src/limits.rs:48) and `JointControlEntry` default literal 0.005 (marengo-config/src/lib.rs:1497) — inconsistent defaults; the 0.005 path (`limit_margin_from_config(None)`, lib.rs:3084) is unreachable while `validate_robot_control_joint_coverage` (lib.rs:570) holds.
- **E3 Envelope dq.** Code (lib.rs:2612-2618) uses whichever of `dq_cmd`/`dq_meas` has larger magnitude, **with that value's sign** (falls back to dq_cmd when |dq_meas| ≤ 1e-9). `docs/safety.md:154` (max magnitude) matches; `ADR 0009:34` ("intent, not laggy feedback") is stale. Side effect: if the arm falls (dq_meas<0) while the command is +small, the *lower* bound shrinks and the upper bound does not — plausible, but undocumented.
- **E4 safety.md:91 Active refusal.** Holds for `apply_limit_patch` (limit_envelope.rs:19), `restore_limit_snapshot` (:107), `rebuild_limits` (lib.rs:737). `rebuild_limits` Active refusal has no test.
- **E5 ADR 0010:39.** `marengo-config/src/lib.rs:797-804` rejects `position_trajectory_velocity_rad_s > cap + 1e-9`; called at Davout build (lib.rs:584), `rebuild_limits` (lib.rs:742), `apply_limit_patch` (limit_envelope.rs:58). Test `marengo-config/src/lib.rs::tests::trajectory_velocity_above_effective_cap_rejected`. Note `restore_limit_snapshot` (limit_envelope.rs:111) calls only `validate_safety_config`, not `validate_control_against_limits` — check whether safety validation covers the trajectory-cap rule (lead).
- **E6 E-stop.** safety.md:8 "latched until documented reset": code latches `HardwareEstop` with no reset at all (faults.rs:223 "No reset"; `recovery_available: false` faults.rs:375) — stricter than doc; "documented reset procedure" does not exist (process restart is the only clear). safety.md:152 confirmed: only callers of `set_hardware_estop` are tests (grep of `bins/` shows only the severity mapping at bins/marengo-pi/src/main.rs:721).
- **E7 τ_ff.** Per-motor_type caps (lib.rs:2666) and rate limit (lib.rs:2668-2674) present and tested (DV-47/48). Seeding (`seed_tau_ff_rate_limiter`, lib.rs:1257-1278) sets history to *measured* torque, so the first output after a seed may jump straight to measured torque (tests/torque_output_contract.rs:229 asserts exactly that) — "rate-limit steps when enabling" (safety.md:68) holds only relative to the seed, not to zero.
- **E8 Danger zones (safety.md:69, :153).** Evaluated on measured q/dq — yes, but when no publishable pose exists `q_meas` falls back to the *commanded* position and `dq_meas` to 0 (lib.rs:2606-2611), so rules silently evaluate against command, not measurement (non-neutral output is then refused by the watchdog in Active; `filter_mit_command` callers outside Active are not). "Clamp **or fault**": no fault action exists — `DavoutError::DangerZone`/`FaultClass::DangerZone` are never constructed (DV-23) and config rejects `action: fault` (marengo-config/src/safety_validation.rs:250-255, test case "unimplemented fault action"). Docs `safety.md:69`, `lib.rs:14` overstate. Master config has one `clamp_velocity` rule (control.yaml:203-211); comm_watchdog_ms = 100.

- **L-1 clamp_velocity does not bound motion.** lib.rs:2780-2786 clamps only the MIT velocity field; with kp>0 the position target still drives at any speed, and with kd=0 (Berthier `kd_mit = 0`, rust-patterns §7) the velocity field has no effect at all. safety.md:153 acknowledges this, yet the only master rule is `clamp_velocity` (control.yaml:210). It also clamps upward (positive) commanded velocity (lib.rs:2783-2785), not just descent.
- **L-2 clamp_torque fallback unit mix.** lib.rs:2788-2791 `max_torque_nm.unwrap_or(max_velocity_rad_s)` uses a rad/s value as Nm. Unreachable while validation requires `max_torque_nm` for clamp_torque (safety_validation.rs:256-261), but `control` is `pub` and `filter_mit_command` does not re-validate.
- **L-3 Limit-patch measured check is effectively dead.** limit_envelope.rs:65-79 reads `last_feedback_samples`, which is only written while feedback motion guards are enabled (Active or armed reference; feedback_consumer.rs:728-731 removes otherwise) and is cleared by every stop (lib.rs:2399). Patches are only allowed when not Active (limit_envelope.rs:19), so in normal operation the map is empty and the "measured q outside proposed hard" guard never fires. The unit test injects the sample by hand (lib.rs:3581-3587). A taught limit can therefore be installed with the arm already outside it; the next Active measured guard (DV-12) would then latch.
- **L-4 Envelope/hard post-clamp guard is unreachable** (E2) — "bug guard" can't detect a soft>hard misbuild because `build_limits` clamps soft into hard (lib.rs:3024-3029); the `soft not within hard` error (lib.rs:3030-3038) is also unreachable after that clamp.
- **L-5 MIT-path envelope clamp untested in Davout.** Only `filter_command` (legacy, uses `q := position_rad`, lib.rs:2813-2814) is tested; `filter_mit_core`'s measured-q/dq_envelope path (lib.rs:2605-2632) has no test asserting a clamped value.
- **L-6 `DavoutError::Estop` unreachable.** Every `hardware_estop` check (lib.rs:859, 1088, 1322, 1343, 1363, 2115, 2246) is preceded by `require_fault_clear`, and asserting E-stop always records `HardwareEstop` (lib.rs:1298). Operators therefore always see `FaultLatched{class: HardwareEstop}`, never `Estop`. Dead variant or ordering bug.
- **L-7 Danger-zone predicate is one-shape only.** lib.rs:2776 fires only on `q > above && dq < below`; "below a position" or "rising" zones can't be expressed. Validator accepts any finite thresholds.
- **L-8 CommWatchdog inside the bootstrap window neither latches nor stops** (lib.rs:1184-1193, stop_after_runtime_error lib.rs:1227-1231). Intended (non-neutral refused, session stays Active). Paired with bins/marengo-pi/src/main.rs:1437-1441, which keeps the control mode on `CommWatchdog` ("preserve_position_hold"): a repeated in-window refusal leaves the owner Active with intent retained — check with SiMarengoPi.
- **L-9 `stop_speed_command` refuses while a reference is busy** (lib.rs:2290) — a stop-style API that can return `ReferenceBusy` without writing anything. The reference owner does its own all-address stop, so impact is low, but it's a stop path that fails closed by *not* stopping.
- **L-10 Unclassified BusError variants don't latch.** lib.rs:1213 `_ => return false`: `InvalidCommand`, `UnknownJoint`, `UnknownMotorAddress`, `DuplicateMotorAddress`, `DuplicateCommand`, `CommandAddressMismatch` from `mit_control_all_at` (lib.rs:2181-2184) or speed writes return Err without a fault or stop. They are pre-send validation errors (nothing transmitted) [INFERENCE — not checked in robstride whether a partial batch could be sent before such an error].
- **L-11 Only first latch stops.** `record` returns true only on empty→latched (faults.rs:303-313). If the first fault's `disable_all` is followed by a re-enable attempt… impossible (FaultLatched), so OK; but a second hazard while still Active cannot exist either since the first latch disables. Low risk; documented here because `poll_feedback` ignores `record_runtime_error`'s return in enable rollback (lib.rs:1533, 1879) and relies on `already_stopped` instead.
- **L-12 MotorFault backstop is redundant and untested.** `state.fault` equals the status flags (robstride/src/mit.rs:166), which already latch `Device` at feedback_consumer.rs:423-434. Also scans *all* configured motors including inactive/stale cache (lib.rs:1992-2010), so a peer's old cached fault refuses the active session — consistent with DV-02 but undocumented.
- **L-13 Enable echo not correlated per write.** feedback_consumer.rs:305-308 clears `enable_echo_pending` on *any* Enable echo for the address once its staggered write is no longer pending; an older echo (e.g. from the reference arm, reference_transaction.rs:1041-1043, or a previous session not fully drained by the bounded pre-enable flush) read after this session's write but before its own echo would arm the strict Run check early. The test `stale_enable_echo_cannot_arm_a_target_not_yet_written` only covers the not-yet-written case.
- **L-14 kp/kd caps compared in joint space.** lib.rs:2599 checks joint-space gains against per-*motor_type* caps; the wire value is `kp / gear²` (lib.rs:2900-2901). Latent (all gear_ratio 1.0 in motors.yaml); same joint/motor-space ambiguity that disabled ADR 0015.
- **L-15 Stop burst size vs RX overflow.** `perform_stop` writes 3 frames per motor back-to-back (lib.rs:2350-2388), each soliciting a reply, the very pattern safety.md:165-176 says overflows the two-frame mcp251x; overflow latches `Transport` (safety.md:217-229). [INFERENCE] an operator Disable on the 5-motor bench could leave a persistent Transport fault. Same for `solicit_status_feedback` (one Disable per motor, unpaced, lib.rs:2453-2461).
- **L-16 `filter_mit_command` is public and mutates limiter state without mode/reference/validation gates** (lib.rs:2550-2566): advances `last_tau_ff`, `wrong_sign_state`, `last_tick` on Ok and keeps them on error; also `f64::clamp` panics if a public-mutated cap/rate is NaN or negative (lib.rs:2933-2942, 1275) — the batch path is protected by `reference_binding_valid` → `validate_safety_config` first, this entry is not. Callers outside davout tests: check (none found in this audit's grep scope besides tests).
- **L-17 Lease TTL unbounded.** `acquire`/`renew` accept any `ttl`; `now + ttl` (active_reporting.rs:230, 267) panics on overflow and a huge TTL is a permanent lease. Only caller passes 30 s (bins/marengo-pi/src/main.rs:525, 533). `validate_ids` checks trimmed length but stores the untrimmed id (active_reporting.rs:226-238, 395-404). Lease caps untested (DV-69).
- **L-18 Echo gating depends on transport capability.** All of DV-07/08/55-58 run only when `bus.echoes_transmissions()` (lib.rs:1474). `MotorBusBackend` returns false off Linux/socketcan (robstride/src/bus.rs:1168-1169) and the router's `.all()` is vacuously true for zero sockets (bus.rs:1518-1521). SimulationBus never echoes, so every sim-based enable test exercises the *non-echo* path; echo behavior is covered only by the `physical_firmware` fake.
- **L-19 Doc gaps.** Feedback-velocity trip constants (3 trips, +0.50 rad/s; lib.rs:325-328), future-timestamp rejection, stop-generation barrier, and enable-reference recheck message (lib.rs:1910) are undocumented; ADR 0009 table default slack 0.03 vs code default 0.005 (E2).
- **L-20 Coverage note.** `limit_envelope.rs` functions 50 % (coverage-by-file.md) — consistent with `urdf_robot()`/restore paths; low coverage on safety code is a gap, not a prune signal.

### Contradictions / leads

#### Answers to the parent's five checks

**(1) Enable identity window.** The code uses `IDENTITY_ADMISSION_TIMEOUT = 100 ms` (crates/davout/src/reference_physical.rs:24) from the first request, `IDENTITY_ADMISSION_RETRY = 10 ms` (:27) and `IDENTITY_ADMISSION_POLL = 5 ms` (:29). The loop is in crates/davout/src/lib.rs:1774-1827. docs/homing.md:134-137 matches the code. **ADR0036:99-101 ("waits up to 50 ms") is stale.**

**(2) ADR0036:57-60 (phase deadlines and fault latching).**
- Deadlines match. Each new phase gets `PHASE_TIMEOUT = 2 s` (reference_transaction.rs:24), capped at `overall − now` (:1751). AwaitEvidence uses the overall deadline (:1748). The deadline renews only on a phase change (:1298-1305). `reference_clock_boundary.rs` asserts the 2 s value and the cap; non-renewal is only implied by the TimedOut tests.
- `fail_reference` latches Transport for `Delivery` and `Backend` (:1576-1587). Readback, Identity, BindingChanged, Hazard and IncompleteReceive do not latch here. Readback and duplicate-UID failures assert `!has_latched_fault` (physical_reference.rs:416, :426, :454).
- **Divergences:**
  - The BaselineStop `Delivery` failure bypasses `fail_reference` (:933-941). It latches only `StopDelivery` through perform_stop, not Transport.
  - `Reporting` failures also latch Transport (:981), which the ADR does not mention.
  - No test asserts the Transport latch for Delivery or Backend.

**(3) Discontinuity bound (ADR0036:102-105).** The bound is built at lib.rs:511-513 (`velocity_scale/gear`, `2·feedback_position_step/gear`) and checked at reference_physical.rs:232-243. The jump case is tested by `coordinate_discontinuity_after_grant_revokes`. The at-rest-across-work branch (:233-235) has no dedicated test.

**(4) Trusted coordinates (ADR0036:125-131).** Implemented at feedback_consumer.rs:67-75 and :838-845, with the phase mapping at reference_transaction.rs:1110-1114. **Untested.**

**(5) ADR0006:55-56.** The ADR says "`set-zero` writes calibration record and marks joint Verified" and that motor-repl enable requires Verified, and its status is still "Accepted" (0006:3) with no supersession note. Code supersedes it:
- `calibrate_joint_zero` writes the SQLite reference journal, not `zero_registry.yaml` (lib.rs:890-950).
- The grant is process-local (reference.rs:93), and Verified comes only from the private authority (lib.rs:646-656).
- docs/safety.md:43-47 and docs/homing.md:116-118 state that grants do not cross processes.

ADR0006 needs a superseded-by note (ADR0022/0023/0036).

#### Other leads

- **RF-57 has no type-level prevention.** `encode_write_parameter` (crates/robstride/src/params.rs:126-175) permits `ZeroSta`/`AddOffset` writes, because `is_read_only` covers only MechPos (:81-83). Public `write_parameter_at` (bus.rs:506) and raw `send_frame` (bus.rs:261) are reachable from any MotorBus user, including bins and tools. "Never sent" rests on code review alone, and no test guards it. A cheap fix would be to make both read-only in robstride, or add a negative test in physical_reference.
- **Error propagation can leave an armed reservation without a stop.** In `advance_reference`, `?` exits return `Err` with the reservation live and possibly armed, with no `finish_reference`:
  - `acquire(...).map_err(DavoutError::from)?` (:1099-1101)
  - "installed target disappeared" (:1052-1054, :1107-1109)
  - `motor_position_scale(motor)?` (:1336)
  - `phase_deadline(...)?` (:1300)
  - "invalid receive phase" (:1285-1289)

  `calibrate_joint_zero` then maps the error to `HomingVerify` and returns (lib.rs:924-931) **without `disable_all`/cancel**. Only the InProgress-deadline branch disables (:940-946). The target can stay enabled until the caller disables. Check whether the marengo-pi and motor-repl callers always disable on Err.
- **Swallowed errors on safety paths:**
  - `abort_reference_for_hazard` uses `let _ = self.finish_reference(...)` and `let _ = self.perform_stop(false)` (reference_transaction.rs:1444-1447).
  - `cancel_reference_for_shutdown` uses `.ok()` (:1428).
  - `finish_reference` uses `let _ = self.observe_staged_reference()` (:1567).
  - `latch_control_fault` stops only when `first` (lib.rs:1170-1176); a later control fault on an already-latched owner performs no new stop.
  - `reference_request_preflight` uses `let _ = self.reference_binding_valid()` (lib.rs:1086). This is intentional, observation only.
- **Saturating counters can stall epoch and generation advance:**
  - `record_identity`, `observe_position` and `record_calibration_mode` use `epoch.saturating_add(1)` (reference_physical.rs:145, :245, :262). At u64::MAX, a UID change, discontinuity or Calibration mode no longer changes the epoch, so `current != Some(binding.device_epoch)` would not revoke. This is practically unreachable, because `begin_new_coordinate` uses checked_add.
  - `ReferenceAuthority::bump_generation` saturates (reference.rs:157). At MAX the revoked flags still hold, so this fails closed.
- **Non-echoing physical bus skips gates.** AwaitReportingOff, the `POST_SET_ZERO_QUIET` Enable hold and `note_set_zero` all apply only when `bus.echoes_transmissions()` (reference_transaction.rs:954, :1018, :1058, :1219; lib.rs:1474). The trait default is `false` (crates/robstride/src/bus.rs:281-283). A physical owner on a non-echoing transport, such as a mux where any socket lacks echo (bus.rs:1518-1521), would skip the post-SetZero quiet and the Off-settle gate. Likewise `verify_physical_identities` could land in the 48-57 ms blackout with only the 100 ms retry window.
- **AwaitAck accepts any type-2 popped after SetZero** with \|q\| ≤ tol (reference_transaction.rs:1258-1266). It does not tie that frame to the SetZero, so a late Enable status for a joint already near zero would pass as the ack. The independent readback (RF-30) mitigates this. The `stale_pre_set_zero_status_is_not_an_ack` test relies on the stale pose being out of tolerance.
- **`verify_physical_identities` bus-error path.** A `get_device_id_at(address)?` error (lib.rs:1819) returns without revoking or latching. No Enable is sent, so this fails closed for motion. It diverges from the doc's "missing UID revokes".
- **The return value of `observe_position` is ignored** in the feedback consumer (feedback_consumer.rs:578-583). Revocation relies on the epoch compare at the next `reference_binding_valid`. Between the frame and the next validation, `contains()` alone (reference.rs:213) does not re-check the epoch. Every admission path calls `ensure_reference_binding` first, so this is fine if no path calls `require_reference_permission` without `reference_binding_valid`. Audit `require_reference_permission` callers.
- **`ack_pop_order` is silently clamped**: `u32::try_from(physical.ack_order).unwrap_or(u32::MAX)` (reference_transaction.rs:1714). Journal evidence is clamped instead of refused, unlike `raw_pop_order` (:1694-1695 → CounterExhausted). This affects history fidelity only.
- **Initial virtual coverage at shutdown.** `cancel_reference_for_shutdown` revokes only when `consumed_bindings` is non-empty (:1414-1416). For INITIAL virtual coverage without a journal, shutdown does not revoke. This is simulation only.
- **Dead legacy permission in the registry.** `HomingRegistry::record_verification` sets the registry to `Verified` (registry.rs:189), and `require_ready` treats that as a "legacy same-process grant" (tests/reference_history.rs:209). Neither Davout nor the bins call `require_ready` or `all_verified` (grep: tests only). It is dead and misleading; candidate to remove or rename.
- **Registry writes are not atomic.** `persist_record` uses `fs::write` with no temp+rename or fsync (registry.rs:209-212). A crash mid-write can corrupt history, and the next start then refuses construction (HM-03). That fails closed, but bricks startup until manual repair (ADR0022:69 acknowledges this).
- **`mark_fault` discards the message** (`let _ = message`, registry.rs:118-121).
- **Docs:**
  - docs/safety.md:21 and the "Enable/disable sequence" (:49-55) still describe registry-style "all joints Verified → Ready". The code requires all `robot.yaml` joints granted by Davout authority (lib.rs:862-863), which matches in effect but not in source of truth.
  - ADR0028 and ADR0030 (assigned as sources) concern capture chronology and store recovery. They hold no reference or grant invariants.

### Contradictions / leads

- **L1 GravityComp is not hard kp=kd=0.** docs/safety.md#Upright-pose incident and ADR 0004 table say GravityComp is `kp=0, kd=0`. In code, kp/kd come from YAML `gravity_comp` (gain_runtime.rs:359-360). A 20-tick ramp from the previous mode's gains also applies inside GravityComp (gain_runtime.rs:157-170, 383-385; mit_feedforward.rs:49). `mit_feedforward.rs::gravity_comp_uses_pre_resolved_wire_gains` asserts kp=9/kd=1.5 pass through, and `resolve_all_gravity_comp_ignores_override_but_accepts_ramp` pins the ramp. So Impedance→GravityComp carries impedance stiffness for about 100 ms, and a YAML edit can make GravityComp stiff with no refusal.
- **L2 No elevated-arm guard and no τ_g sign-test gate in Berthier.** τ_g goes on the wire in Position, Impedance and GravityComp with no per-joint sign attestation (position_feedforward.rs:64, mit_feedforward.rs:49,60). The safety.md upright-incident item 3 sign test exists only as a `sign-tested` token in bins/marengo-pi and bins/motor-repl. Nothing in Berthier stops Position mode at elevated q.
- **L3 PositionTrace can do blocking I/O inside the 200 Hz tick.** `flush()` is dead, but the 512 KiB `BufWriter` flushes itself synchronously inside `maybe_record` when full (position_trace.rs:32, 56), and that is called from `tick_inner` (loop.rs:1303-1342). The write error is discarded with `let _ =` (loop.rs:1337), open failure is swallowed by `.ok()` (position_trace.rs:20), and the final flush happens on drop. The trace cost is measured in `trace_us` but not bounded. Env-gated (`MARENGO_POSITION_TRACE`).
- **L4 Fail-open defaults on the motion path:**
  - `clamp_limits_for` uses `unwrap_or(f64::MAX)` when motor_type_defaults is missing (loop.rs:1001-1003), so overrides go unclamped in Berthier.
  - Position mode uses a hardcoded impedance kp=20, kd=1 for a joint missing from control.yaml (loop.rs:1153-1157).
  - `clamp_hold_target` returns the requested target unclamped without a limit policy (loop.rs:599-601).
  - `HoldJointParams` defaults are inconsistent: slew `unwrap_or(0.15)` at loop.rs:515 versus 0.25 at 617/1194.
- **L5 No finiteness checks on Berthier position inputs.** `set_joint_position_setpoint`/`enter_position_hold_at` accept a NaN `position_rad` (loop.rs:492-584). `start_position_wave` NaN `min_rad`/`max_rad`/`half_period_sec` pass the `>=`/`==`/`<=` checks (loop.rs:645-653). Safety relies on downstream Davout/robstride rejection (RS-01).
- **L6 Some errors neither latch nor discard intent (loop.rs:1048-1057):**
  - `MissingSetpoint` (including `LenMismatch` relabelled `joint:"len_mismatch"`, loop.rs:91-93) and `Dynamics` (gravity_torques at 1141) leave Position mode armed. Every tick then errors before `send_mit_batch`, so no MIT or keepalive is sent until Davout's comm watchdog or the drive CAN timeout acts.
  - `Chappe` publish failure (loop.rs:1433) returns Err after MIT was already sent; whether that is fatal is the caller's choice.
- **L7 HoldTracking latch path and reason strings are untested.** No ControlLoop test reaches `LoopError::HoldTracking` (only unit tests in position_hold_tests/hold_tracking.rs). None of the three `latch_control_fault` reason strings (loop.rs:1035, 1039, 1043) is asserted or documented.
- **L8 AscentStall covers positive-direction outbound moves only.** `to_target > return_settle_band` (position_hold.rs:1066-1068) uses `target − q`. A stalled negative outbound move is caught only by HoldTracking, which also needs the net torque to oppose the target. This matches the safety.md wording ("above q"), so it is an asymmetry to note rather than a doc conflict.
- **L9 Joints without feedback read as q=0.0.** `read_positions` uses `unwrap_or(0.0)` (loop.rs:1477-1487). That q=0.0 feeds `gravity_torques(&q)` for active joints in coupled chains `[INFERENCE: wrong τ_g if an inactive proximal joint is not at 0]`, and feeds hold arming for inactive peers. `set_joint_position_setpoint` on an inactive peer is admitted (tests/cs24_inactive_peer.rs:113 shows `is_ok`).
- **L10 `set_control_mode` silently ignores requests while `reference_busy`** (loop.rs:772-774). It returns `()`, so callers such as `enter_position_hold` would continue unless an earlier refusal fired.
- **L11 `assert_eq!` panics in the realtime path.** gain_runtime.rs:199 and 244 (`wire_gains_now`, `resolve_all`) can panic. Unreachable today because both sides come from `joint_names`, but this conflicts with the "no unwrap in crates" rule.
- **L12 Hold-at after an operator or non-fault Davout disable silently re-enables drives** (`ensure_active_for_motion`, loop.rs:712-721; test `hold_at_reenables_after_safety_disable`). This is intended per the doc comment, but it means a motion command implies Enable.
- **L13 Robstride saturates finite out-of-range MIT values instead of rejecting them** (mit.rs:74, 88; doc comment 25-27). For example, kp=6000 on RS03 goes on the wire as kp=5000, and position beyond ±4π wraps to the end code. No test covers saturation. Davout must bound every field.
- **L14 "zero_sta/add_offset writes and type-22 saves are never sent" (safety.md:40-41) holds only because nobody calls them:**
  - `encode_write_parameter`/`write_parameter_at` accept `ZeroSta` (U8) and `AddOffset` (finite F32) (params.rs:38-40, 132-174).
  - `pack_ext_id(22, …)` plus `CanBus::send_frame` are public.
  - The guarding test `davout::no_comm_type_22_in_robstride_surface` checks only `from_u8(22)`.
- **L15 Silent drops in the receive classifier:**
  - Unknown comm types are dropped without even a trace (bus.rs:708-710), while other skips log `trace_skipped_frame`.
  - Status from a configured device id on an unexpected interface, or an ambiguous id with no interface, is dropped (bus.rs:750-761, 951-970).
  - Both rely on Davout feedback watchdogs.
- **L16 Socket-queue drops are invisible.** The SocketCAN backend does not enable `SO_RXQ_OVFL` or any drop counter (grep: none). Only controller-level overflow error frames (`CAN_ERR_CRTL_RX_OVERFLOW`) surface `[INFERENCE: kernel socket-buffer overruns are not error frames]`.
- **L17 Gated or ignored tests.** `tests/socketcan_conversion.rs` is `cfg(feature="socketcan", linux)` and the vcan tests are also `#[ignore]`. In the default `cargo test`, FD rejection, DLC checks, error-frame conversion, `CAN_RAW_RECV_OWN_MSGS`/loopback/error-filter configuration and atomic write are not exercised.
- **L18 Sleep inside the tick.** `drain` calls `std::thread::sleep` between idle rounds for positive-budget polls (receive.rs:189-195), and this runs inside Berthier's tick through Davout `drain_feedback`. It is bounded by the deadline, but it is jitter in the 200 Hz loop.
- **L19 Unreachable branch.** `decode_fault_report` returning None leads to `continue` (bus.rs:817-819), which cannot happen after the exact-8-byte check at 781. It is harmless, but it would silently drop a type-21 frame if the order of checks changed.
- **L20 Unaddressed and default routing paths skip route checks:**
  - `SocketCanRouter::send_frame` with one interface sends unaddressed frames without checking the address set (bus.rs:1444-1451).
  - Unaddressed `mit_control_all` never calls `validate_address`.
  - The default `CanBus::validate_address` is `Ok(())`.
  - No production caller uses these paths (grep).
- **L21 Raw ID construction outside robstride.** `crates/davout/examples/can_tick_bench.rs:37` builds `(2 << 24) | (2 << 22) | …` by hand. It is the only one outside tests, and it builds synthetic RX only, not TX.

### Contradictions / leads

- **L-01 Chappe enable skips the gravity-saturation preflight.** Stdin `enable` refuses on saturation unless `force` (main.rs:881-887). `handle_chappe_enable` (main.rs:339-358) has no preflight, so Consul/gateway enable bypasses the only τ_g-vs-limit enable gate. codemap.md:11 claims "Preflight … before enable" without qualification.
- **L-02 Preflight is fail-open** (main.rs:834, motor-repl/main.rs:49). If `max_gravity_torque_over_range` errors, `unwrap_or(0.0)` treats it as zero torque and passes. `filter_map` (main.rs:818-828) silently skips joints with no motor entry or limit policy. The ranges come from `motor.bench.position_*` rather than Davout's effective envelope (URDF ∩ bench).
- **L-03 Error swallowed on tick fault:** `let _ = loop_ctrl.supervisor_mut().disable_all();` (main.rs:1436). Davout presumably records the StopReport, but marengo-pi neither logs nor publishes a stop-delivery failure here.
- **L-04 CommWatchdog keeps the Berthier mode** (main.rs:1437-1441), e.g. Position. docs/safety.md:70 says "CAN receive timeout → Disabled". The supervisor is Disabled, but on re-enable the retained Position intent can resume. Needs a check that Berthier re-seeds the setpoint from measured `q` (it likely does; unverified).
- **L-05 Cross-kind coalescing can drop a limit_patch's motors/URDF write.** `enqueue` replaces any pending request (limit_persist.rs:265). Scenario: a limit_patch (`motors: Some`) is still pending when a ConfigOverlay `persist=true` (`motors: None`) arrives. The second write is control-only, so motors.yaml hard bounds and the URDF expand are never written. The Durable that follows is `config_persist`, not `limit_patch_persist`, so the gateway's live-wait gets no matching terminal for the patch. Gateway `state.rs:209-216` also clears `persist_degraded` on any Durable. ADR 0017 §3 is coalesce-safe only between two motors-bearing requests. Untested: `persist_queue_coalesces_to_latest_draft` is control-only.
- **L-06 Chappe disable error path skips `set_control_mode(Disabled)`.** `result.map_err(...)?` at main.rs:362 returns before :363, so GravityComp/Position intent survives a failed Chappe disable. Stdin disable sets Disabled unconditionally (main.rs:904). Asymmetry.
- **L-07 Deferred commands replay after a failed reference.** A deferred `enable`/`hold-on` typed during referencing runs after `reference X failed` (reference_queue.rs:136-142 only discards on `cancel`). This is asserted as intended by `stdin_defers_while_busy_and_replays_after_failure`. Davout should refuse an enable without a grant, but operators may not expect it.
- **L-08 Lagged Chappe channels drop safety commands silently.** On `enable_rx`, `homing_rx` and `testing_cmd_rx`, `let Ok(bytes) = rx.try_recv() else { break; }` (main.rs:482, 499, 582) treats `Lagged` like `Empty`: no warn and no audit. A lagged `enable=false` (disable) request can be lost. Undecodable envelopes are also dropped with no log (main.rs:485-490).
- **L-09 Typed Davout errors become strings.** `apply_limit_patch` errors, including `LimitPatchActive` and `ReferenceBusy` from `refuse_reference_interference`, are wrapped as `ConfigError::Parse` (overlay.rs:429-437). Clients cannot distinguish an Active refusal from a parse error except by text.
- **L-10 Empty `expected_revision` bypasses Pi-side CAS** (overlay.rs:403). The gateway fills it with the current revision when absent (gateway limit_patch.rs:146-149), so direct Chappe publishers skip CAS. ADR 0033: the Pi trusts every Chappe publisher. The overlay trust-boundary note is at overlay.rs:13-15.
- **L-11 PositionTrace still does I/O on the control thread.** `PositionTrace::maybe_record` (crates/berthier/src/position_trace.rs:47-58) writes into a 512 KiB `BufWriter` from `tick`. When the buffer fills, a synchronous `write(2)` happens on the 200 Hz thread. There is no explicit `flush()` (dead_code at :60-63), so AGENTS.md:197's letter is met but not its spirit. The file is never flushed on shutdown (BufWriter drop flushes only on normal return).
- **L-12 docs/safety.md:72 "Exit: disable_all on process exit / SIGTERM" is false for motor-repl** (MR-02). For marengo-pi it holds only for SIGINT/SIGTERM with `disable_on_exit: true`. SIGKILL or a panic skips it, and the drive-side CAN timeout is unverified (reviews/2026-09-29/control.md:286).
- **L-13 Stdin EOF does not trigger shutdown.** The reader thread just breaks (main.rs:317-319). `cmd_rx.try_recv().ok()` then turns `Disconnected` into None forever. A `pi_marengo_pi_script` that omits `quit` leaves marengo-pi running until SIGTERM.
- **L-14 Overrun has no consequence** (PI-51). A tick that exceeds its period is only counted at debug level. There is no deadline watchdog in the outer loop, and Chappe/overlay drains are unbounded per tick (`loop` until Empty), so a command flood stretches the tick. ADR 0024:20 and safety.md:120 explicitly disclaim flood priority.
- **L-15 Safety publication cadence.** SafetyState is published only at `chappe_state_hz` and only after a tick. A tick error message is reported only if Davout has no retained fault. A transient tick Err that Davout does not latch disappears on the next healthy tick (`active_fault` is reassigned each loop, main.rs:1432-1444).
- **L-16 Reference-queue E-stop cancel does not stop Davout's in-flight transaction** (reference_queue.rs:154-156, 202-203 "Callers stop the owner's transaction themselves"). `pump` is the caller here and issues no stop; this relies on Davout's own E-stop handling. Moot until PI-53 is wired.
- **L-17 Testing and lease paths are not gated by the reference queue at the Pi level.** `drain_testing_commands` and lease/status-poll handlers run while the queue is busy and rely on Davout `refuse_reference_interference`/ReferenceBusy. Unverified for `enter_position_hold_at` / `apply_gain_override` during a reservation.
- **L-18 Coalesced Pending ACKs never resolve.** An earlier `limit_patch` Pending whose request was coalesced gets no `limit_patch_persist` terminal (limit_persist.rs:109-110 comment). The gateway's ACK wait must time out, which is honest but surfaces as a failure.
