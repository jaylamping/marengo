# Marengo context

Shared glossary for workflow and product language. Expand only when a term is
resolved in conversation or an ADR.

## Glossary

| Term | Meaning |
|------|---------|
| **Software home** | The host checkout used for software and tracked CAD sources: `J:\code\marengo` on this Windows machine, and a host checkout of the same remote on macOS. Local CAD also lives under `J:\code`. See [ADR 0018](docs/decisions/0018-windows-macos-software-home.md). |
| **CAD session** | A Windows editor opened on `J:\code\marengo`, with SolidWorks MCP (COM) using that same local CAD tree. |
| **Software session** | A Windows or macOS editor opened on the host checkout. Rust, Consul, and MCP tools run on the host where supported; Docker runs the Linux workspace checks. |
| **Portable MCP config** | Repo [`.cursor/mcp.json`](.cursor/mcp.json) uses `${workspaceFolder}` and launchers only. Host-specific Pi defaults belong in `tools/marengo-pi-mcp/src/launch.ts` (compiled to `dist/launch.js`, plus `run-mcp.sh` / `run-mcp.ps1`), not in that JSON env block. |
| **Position hold** | Berthier’s joint-space motion primitive for `ControlMode::Position` (operator hold-at / hold-on): trapezoid advance policy plus MIT composition. Rust module/type: `PositionHold`. Not a separate control mode. _Avoid_: HoldExecutor, Controller (for this concept). |
| **MIT feedforward** | Berthier’s Active MIT packing for `GravityComp` / `Impedance` / `TorqueOnly`: mode gains (hard-zero under GravityComp/TorqueOnly) plus τ_ff composition (`τ_g` vs operator `τ_cmd`). Rust module/type: `MitFeedforward`. Not dynamics (`armee-dynamics` owns τ_g). _Avoid_: GravityCompCompose, Controller (for this concept). |
| **GainRuntime** | Berthier runtime gains: Testing overrides + mode-transition ramp + per-tick resolve. Types `GainRuntime` / `ResolvedGains`. Not a control mode. `ControlLoop` keeps the Pi facade. Not MIT compose (`MitFeedforward` / `PositionHold`). _Avoid_: stashing override/ramp on `MitFfJointIn`. |
| **Joint feedback** | Davout’s joint-space sample for one actuated joint after motor→joint conversion (position, velocity, torque, temperature, fault). Control and Chappe publish read this; they do not address the bus. Rust type: `JointFeedback`. _Avoid_: MotorState (robstride wire/cache), JointState (proto wire), motor_states map. |
| **Actuator facets** | Per-actuator status is orthogonal: **presence** (Offline/Online), **reference** (Unready/**Ready**/Faulted — Ready ≡ homing Verified), **drive** (Disabled/Active), **health** (Nominal/OutOfLimits/Fault/…). Not one progressive enum. Hardware shows a derived primary badge (Fault > OutOfLimits > Offline > Active > Ready > Online). _Avoid_: Inventory static Enabled/Offline labels; conflating Ready with Active. |
| **Joint Ready** | Reference commissioning complete for one actuator (firmware Set Zero accepted + homing Verified). Does not mean the drive is Active. _Avoid_: Enabled, OperationalMode Ready (robot-level). |
| **Limb Ready** | Aggregation over an anatomical limb group from master SoT (e.g. `right_arm`): every Online / motors-mapped joint in that group is Joint Ready. Offline/unbuilt joints in the group do not block Limb Ready. |
| **Robot Ready** | Aggregation: every master-SoT actuated joint is Joint Ready. Honest full-robot status. Enable of a partial build may use an explicit **commissioning override** when Robot Ready is false (e.g. left toe offline while testing upper body) — never a silent skip. |
| **Commissioning scope** | Operator-selected limb(s)/joint set on Hardware that Enable is allowed to command when Robot Ready is false. Persists across marengo-pi restart until cleared; requires confirm when first applied or widened. Never includes Fault or OutOfLimits joints. Status still shows true Robot Ready separately. Drive **Active** never auto-restores after restart/crash — operator uses **Enable all Ready-in-scope**. _Avoid_: silent JOINT_SUBSET-only Enable; auto-enable on boot. |
| **Hardware page** | Consul's table-first durable surface for the master URDF/YAML description, warn-only completeness, staged import/resolution/archive, Set Limits, Set Zero, actuator facets/Ready, and commissioning scope. It offers an optional 3D view. Telemetry remains live read-only observation. |
| **Telemetry page** | Consul live read-only observation (ex-Subsystems). No Set Limits / Set Zero / membership SoT. Route `/telemetry`; `/subsystems` redirects. _Avoid_: Inventory table; Subsystems as nav label; separate Actuators page (use Hardware filters if needed). |
| **Set Zero** | Durable Hardware action: firmware encoder zero at the current pose → calibration record → Joint Ready. Requires sign attestation; refused while Active. _Avoid_: Home (ambiguous). |
| **Go-to-zero** | Ephemeral motion that commands a joint toward `q = 0`. Not a reference action; stays off Hardware (Testing / similar). _Avoid_: calling this Home or Set Zero. |
| **Coupled gravity compensation** | Limb-level GravityComp acceptance after per-joint checks: all online/mapped joints in the limb in `GravityComp`; three-band static poses (arm-down, mid-range, elevated) with per-joint `|τ_meas − τ_g| < 0.20 Nm`, limb RMS residual `< 5%` of peak `|τ_g|`, and light dwell (≈5–10 s, drift `< 0.05 rad`); plus slow hand-guided float with feel + residual spot-checks. Not a separate control mode. _Avoid_: treating single-joint checks alone as limb G-comp done. |
| **Commissioning velocity baseline** | Manual@V derated per-joint reference that **sizes** Position-ladder rungs. Effective rung speed is `min(% × baseline, live safety ceiling)` — see **Commissioning ladder speed**. Not a license to raise Davout/MIT caps in the ladder chapter. |
| **Limb-standard payload** | Tip-mounted commissioning fixture in the **0.5–0.8 kg** assembled band, weighed on every attach; mass written into the active model before payload gates; unweighted model restored after. Not a single plate SKU. _Avoid_: treating any unweighed tip load as the standard. |
| **Payload critical gates** | Minimum weighted re-check after tip-load URDF/COM sync (`pi_sync_bench_urdf` + gravity verify): coupled G-comp (same bars), Position at effective **50%**, near-limit at effective **25%**; restore unweighted model and re-verify. Not a full mode re-commission. _Avoid_: YAML-only sync; leaving weighted mass live. |
| **Limb commissioning playbook** | The limb-parameterized hybrid SoT procedure spine at `docs/commissioning/limb-playbook.md` (Reference → … → Limb sign-off). Supersedes retired fragmented `docs/bench-*.md` suites. _Avoid_: treating `docs/pi-commissioning.md` (Pi OS/bring-up) as the limb motion playbook. |
| **Wave-pose G-comp** | Playbook §4c gate: elevated multi-joint GravityComp at `wave_pose` with §4b residual bars. Necessary but not sufficient for Consul `WAVE_POSE_GCOMP_SIGNED` — also requires a documented live raise + elbow-wave smoke after the redesigned Wave preset. Not a separate control mode. _Avoid_: flipping the Wave flag from §4c alone; calling this “E6”. |
| **Commissioning ladder speed** | Effective Position-ladder rung speed = `min(% × commissioning_velocity_baseline, live safety ceiling)` (`velocity_max`, cruise ceilings, danger-zone clamps). Baselines size rungs; they do not raise Davout/MIT caps in the ladder chapter. |
| **Pi URDF library** | The installed hardware-description directory at `{MARENGO_ROOT}/assets/urdf/` (normally `/opt/marengo/assets/urdf/`). It contains the master URDF, staged uploads, and contributor archives. Consul reads installed files through the gateway; repository/deploy copies must be reconciled with Pi edits. |
| **URDF seed** | Repository-tracked initial robot-description files used by deployment to populate the installed library. Installed master changes can diverge from the checkout; deploy preservation and explicit replacement policy determine which copy wins. |
| **Master URDF** | The combined hardware-description file `assets/urdf/marengo.urdf`, alongside the master YAML set. Hardware import matches contributions by joint name, resolves supported field differences, archives the contributor and previous master, and promotes the merged file on disk. A successful URDF import requires a runtime restart to load the new geometry/dynamics model. |
| **Master YAML set** | The installed `robot.yaml`, `motors.yaml`, `control.yaml`, and `homing.yaml` under the selected master config directory (normally `/opt/marengo/config/`). They define joint membership, motor addresses/transforms, control policy, and reference settings alongside the master URDF. |
| **Bringup profile** | Retired as the durable hardware-description source. Commissioning subsets use the master description and explicit commissioning scope / supported joint-subset controls. Archived contributors and older slices are history, not independent live robot descriptions. |
| **URDF staging** | Upload bytes held under `assets/urdf/staging/<upload_id>/` while the operator reviews their proposed merge. Staging alone changes neither the master file nor motor output. |
| **URDF archive** | Accepted-contribution history under `assets/urdf/archive/<upload_id>/`, including contributor bytes, the replaced master, and provenance/checksums. Restoring an archive opens a new staged import for review. |
| **Assembly identity** | The structural joint-name overlap used to compare a contributor URDF with the master. Filename is a storage label. Motor CAN addresses and eligibility remain defined by the YAML configuration; matching a URDF name does not establish a physical actuator reference. |
| **Mapped URDF fields** | Joint fields represented by the current merge preview and resolution model, including supported parent/type/origin/axis/limit differences. Completeness warnings inspect additional model/config facts. Link inertials, visual/collision changes, and topology handling must not be assumed to have complete field-level merge support. |
| **Incoming changes** | Contributor field differences proposed in an upload preview. Choosing master keeps the existing value; choosing contributor selects a supported incoming value. Accept commits the reviewed merge to the installed master file and reports whether restart is required. |
| **Resolve wizard** | Hardware's upload review flow: stage contributor, inspect joint overlap and differences, choose resolutions for supported kinematics-critical fields, then Accept or cancel. The preview itself is not a motor-enable command. |
| **Import gate** | The review/validation step before a contributor is promoted into the master. Current implementation requires resolutions for kinematics-critical differences and checks supported structural invariants. Completeness remains warn-only; a parsed import does not prove physical sign, calibration, or full dynamics correctness. |
| **Accept URDF** | Promote the resolved merged master file on disk after archiving contributor/previous bytes. The gateway's successful response currently sets `restart_required: true`; the Pi runtime reloads the model on restart and begins Disabled. Operational drive Active still requires an operator enable sequence. |
| **URDF activation failure** | The activation request failed. Archive or master bytes may already have changed, including when validation fails after promotion; verify the installed checksum before retrying. This differs from live limit-patch persistence degradation. |
| **Live limit patch** | A numerical hard/soft/torque/velocity policy change applied to Davout while Disabled, with async persistence to motors/control/expand-only URDF. Pending is live acceptance; Durable confirms write completion; Failed means live/disk state may differ. General URDF import uses the separate restart-required path. |
| **Make Active** | Retired as a Config/Setup assembly-switching control. Hardware's Accept URDF action promotes the single master description; it does not mean motor drive Active. |
